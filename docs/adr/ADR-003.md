# ADR-003 — Identidad, sesiones y matriz de roles

- Estado: accepted (especificación revisada aprobada)
- Aprobación humana: 2026-07-23; enmienda de flujo cliente aprobada el 2026-07-27; flujo interno y especificación revisada aprobados el 2026-07-29
- Fecha: 2026-07-21
- Decisores: usuario (aprobación), Leader y Architect Reviewer (recomendación)
- Relacionado con: feat-002

## Contexto

Hay clientes autoservicio y personal interno. Los roles solos no alcanzan: la autorización depende también de propiedad de la orden, asignación y transición solicitada.

## Drivers de decisión

- Menor riesgo al manejar credenciales.
- Inicio de sesión de baja fricción para clientes.
- MFA y cuentas aprovisionadas para personal interno.
- Autorización auditable y controlada por el backend.

## Opciones consideradas

1. Identidad propia: máximo control, riesgo y trabajo injustificados.
2. AWS Cognito: proveedor administrado alternativo, sin integración especial con el VPS elegido.
3. Auth0: identidad administrada, OAuth/OIDC y menor acoplamiento a la nube.

## Decisión

Usar Auth0 exclusivamente para autenticación OIDC. MVP: pantalla propia con código OTP por email para clientes, sin registro visible; cuentas internas de base de datos aprovisionadas por un ADMIN con contraseña y MFA obligatorio, aplicado selectivamente por la aplicación administrativa. Google queda fuera del MVP y se reconsiderará antes de producción mediante una decisión y validación no productiva separadas. Mantener en PostgreSQL los perfiles y roles activos `CLIENT`, `DISPATCHER`, `ADMIN`, con permisos explícitos. El técnico asignado es un registro operativo sin acceso al sistema; `WORKER` queda reservado para una fase futura. La API valida issuer, audience y expiración del token y luego aplica autorización contextual sobre recursos; no confía en ocultamiento de UI ni en un rol aislado del proveedor.

## Consecuencias positivas

- PIGAR no almacena contraseñas.
- Separación clara entre identidad y reglas del negocio.
- Matriz de permisos testeable con casos negativos.

## Costes y riesgos

- Dependencia y coste de Auth0.
- El alta/baja de usuarios con acceso exige sincronización idempotente entre identidad y perfil local.
- SMS/WhatsApp OTP queda fuera del MVP para no sumar otro proveedor y riesgo de abuso. El OTP por email es una capacidad de Auth0 ya aprobada; no agrega proveedor.

## Enmienda de flujo — 2026-07-27

El usuario aprobó sustituir magic link por código OTP de email para clientes.
Motivo: el flujo es familiar para usuarios y permite conservar Universal Login,
compatible con MFA selectivo de administración mediante Actions. Esta enmienda
no habilita implementación ni uso productivo.

## Enmienda de cuentas internas — 2026-07-29

El usuario confirmó sustituir Auth0 Organizations/invitaciones por cuentas
internas aprovisionadas por un ADMIN. El usuario interno inicia con usuario o
email y contraseña hospedada por Auth0, seguido de MFA TOTP. No hay alta
pública ni cuenta para operarios. La especificación revisada fue aprobada el
2026-07-29.

## Enmienda de alcance de Google — 2026-08-01

El usuario decidió excluir Google del MVP. El portal cliente ofrece únicamente
OTP por email; no se configura ni valida la conexión social de Google para este
incremento. Antes de producción se abrirá una revisión explícita para decidir
si se incorpora Google y, si corresponde, se validará con una cuenta no
productiva sin registrar datos personales, tokens ni secretos. Esta enmienda
de alcance no autoriza cambios de código, proveedores, despliegue ni
publicación.

## Estrategia de salida o reversión

Persistir un `identity_subject` opaco y usar OIDC estándar permite migrar proveedor. Ninguna entidad de dominio referencia IDs internos de Auth0.

## Evidencia/PoC requerida

- Flujos cliente e inicio interno preaprovisionado con MFA.
- Matriz completa de permisos, revocación/baja y pruebas de acceso cruzado.
